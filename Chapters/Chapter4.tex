\label{chapter4}

\section{Implementation Overview}
This chapter details the implementation of the authorization mechanism. The implementation spans
three layers:
(i) ISA extension and decode/execute integration for the \texttt{kc} instruction, (ii) a
verification datapath with protected key storage and an Authenticator FSM, and (iii) host
toolchain and application support for compilation, inspection, authorization exchange, and
programming.

\subsection{Hardware--Software Partitioning}
The implementation partitions responsibilities across hardware and software to maintain a
small trusted computing base. Hardware components enforce authorization and gating, while
software components prepare inputs, initiate the protocol, and maintain audit records. This
partitioning ensures that the enforcement decision is local to the device and does not rely
on external policy enforcement once execution begins.

\subsection{Interface Signals and Control}
Key control signals connect the ISA extension, verification datapath, and gating logic.
These signals remain internal to the device and are not exposed through the normal debug
interface prior to authorization.

\section{ISA Extension and Firmware Support}
Chapter~3 defines the \texttt{kc} instruction semantics and encoding. This section focuses on
implementation integration: wiring the opcode into decode/execute, placing the instruction in
early boot firmware, and ensuring toolchain emission in concrete build artifacts.

\subsection{Opcode Allocation and Encoding}
Assembler and disassembler tables are extended to recognize the reserved \texttt{kc} opcode
defined in Chapter~3, ensuring that the instruction is emitted and displayed consistently in
build artifacts. This avoids opcode collisions and enables straightforward audit in disassembly.

\subsection{Decode and Execute Integration}
The decode path asserts \texttt{kc\_event} and routes operands to the verification datapath.
Integration ensures that the pipeline does not advance past the authorization point until the
FSM resolves the decision and updates gating outputs.

\subsection{Firmware Invocation Pattern}
The boot firmware places \texttt{kc} in the startup path so that authorization occurs before
privileged operations are enabled. Placement is handled during the BootROM build to ensure the
instruction remains in the early-boot path.

\subsection{BootROM Integration}
BootROM integration ensures that the authorization point is executed before application code,
preventing later-stage software from bypassing the gate.

\section{Protected Key Storage and Verification}
Chapter~3 defines the protected key model. The implementation instantiates a dedicated NVM
block, a restricted access path, and a constant-time comparator that exports only a one-bit
\texttt{match} signal to the control logic.

\subsection{Protected NVM Access Path}
The protected key store is excluded from the standard address decode and exposed only through
the comparison interface. The CPU cannot issue conventional reads or writes to this region.

\subsection{Comparator Implementation}
The comparator is implemented with a mismatch accumulator to avoid early exit. A single match
bit is exported to the FSM to drive state transitions.

\subsection{Isolation Properties}
Isolation is verified by the absence of a memory-mapped region and by limiting outputs to the
match bit and internal status signals.

\subsection{Key Provisioning Interface}
Provisioning is performed through a restricted enrollment path separate from normal data
memory transactions, preventing accidental exposure during updates.

\section{Authenticator FSM and Gating Implementation}
Chapter~3 specifies the FSM behavior. The implementation connects the comparator output to the
state logic and routes the resulting gating signals to the execution and debug subsystems so
that privileged capability is released only by on-device control.

\subsection{Debug Interface Control}
The debug enable line is driven by the FSM and is not modifiable by software prior to
authorization.

\subsection{Execution Gate Enforcement}
Execution is released only when the FSM asserts \texttt{exec\_enable}; otherwise, the CPU
remains halted to prevent partial initialization.

\section{Host Workflow and Authorization Exchange}
The host workflow implements the Chapter~3 sequence and integrates build, transport, and audit
functions. The implementation emphasizes modularity and logging for traceability.

\subsection{Toolchain Integration}
Toolchain components are configured to emit and preserve \texttt{kc} so that the opcode is
visible in ELF and HEX artifacts without manual binary patching.

\subsection{UART Protocol Handling}
The UART parser enforces delimiters and ordering; violations trigger a halt and are logged.

\subsection{Logging and Audit Records}
The host logs device identifiers, toolchain metadata, and authorization outcomes for later
traceability. These records provide evidence that privileged access was released only after
successful verification.

\subsection{Host Application Modules}
The implementation uses modular host software components to separate build steps, key
handling, transport, and auditing.

\subsection{Programming and Image Load Sequence}
After authorization succeeds, the host initiates the image programming sequence. The workflow
supports device connection, image selection, and a controlled load step that writes the
verified firmware image. This ordering ensures that programming occurs only after the
authorization gate has been released.

\subsection{Failure Handling}
If any UART message is missing or out of order, the device transitions to \textsf{HALT} and
requires a reset before another attempt is allowed. The host logs the failure and prevents
automatic retries that could mask configuration errors or policy violations.

\section{Implementation Validation and Integration}
Integration validates that the \texttt{kc} instruction is emitted, preserved, and visible in
disassembly, and that the authorization sequence produces a deterministic gating decision. The
validation approach focuses on correctness of the enforcement path and the integrity of the
toolchain-to-device flow rather than on performance benchmarking.

\subsection{Validation Checklist}
The following checks are performed during integration:
\begin{itemize}
  \item Presence of \texttt{kc} in the compiled binary and in disassembly output.
  \item Successful ELF$\rightarrow$HEX conversion without opcode loss.
  \item Correct UART sequence ordering and delimiter handling.
  \item Gating behavior that enables execution and debug only after a match.
  \item Deterministic fail-stop behavior on mismatch or protocol error.
\end{itemize}

\section{Deployment Considerations}
Deployment requires secure provisioning of the reference key and consistent operator
procedures. The implementation assumes that enrollment and provisioning are performed by
authorized personnel and that audit logs are retained for traceability. In field deployments,
the authorization gate provides a device-resident control point that remains effective even
when the device is physically accessible.

\section{Summary}
The implementation integrates a custom ISA instruction, protected key storage, a constant-time
verifier, and an Authenticator FSM to gate execution and debug access. Toolchain support ensures
that the authorization primitive is emitted and preserved across the build pipeline, while the
host workflow provides compilation, inspection, authorization exchange, and programming steps.
Evaluation results and evidence artifacts are presented in Chapter~5.
