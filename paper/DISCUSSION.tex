\section{Discussion}
\label{sec:discussion}

The evaluation artifacts support three core properties: the authorization instruction
is usable through the standard build pipeline, debug enablement is released only after
explicit authorization, and failure is fail-stop with both execution and debug
disabled. These results indicate that authorization is enforced on the device rather
than being only a host-side convention.

The design targets physical-access threats by storing the reference key in protected
non-volatile memory that is not accessible through ordinary load/store operations,
reducing key extraction by untrusted firmware. The ISA-visible trigger makes
authorization explicit and auditable in compiled artifacts, but it also makes the
toolchain and provisioning workflow part of the trusted computing base. Practical
deployment therefore requires controlled toolchain distribution, provenance logging,
and clear lifecycle policies for enrollment and recovery.

Recent work (2019--2025) continues to strengthen adjacent defenses: surveys of secure
boot and TEEs highlight evolving deployment trade-offs~\cite{wang2022securebootsurvey,ahmed2025riscvtee},
authenticated debug mechanisms reduce exposure of invasive interfaces~\cite{lapeyre2022jtagauth},
and newer control-flow attestation techniques provide lightweight runtime evidence of
software behavior~\cite{benyehuda2022nanovised}. In this context, the contribution is
complementary: authorization is bound to an ISA-visible primitive emitted by the
toolchain, so privileged execution and debug access are gated by a device-local
decision rather than host-side policy alone. Table~\ref{tab:discussion-positioning}
summarizes how the approach addresses limitations of earlier lines of work.
