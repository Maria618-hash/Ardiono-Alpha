\section{Related Work}
\label{sec:relatedwork}

Secure boot anchors trust in immutable first-stage code that authenticates later images.
BootROM-based secure boot and surveys emphasize early-stage integrity and practical
constraints in embedded deployments~\cite{bin2020bootrom,rv2018securebootreview}. DICE
and measured-boot approaches extend trust to device identity and boot measurements,
while multi-stage boot-chain protection addresses richer stacks such as embedded
Linux/FPGA systems~\cite{jaeger2020diceharder,parno2010bootstrapping,devic2011fpga,wang2022securebootsurvey}.
These lines of work focus on image authenticity but leave post-boot debug enablement
less constrained under physical-access threat models.

Debug and test interfaces remain high-impact attack surfaces. IEEE~1149.1 defines the
test access port and boundary-scan architecture~\cite{ieee1149_1}, and boundary-scan
test modes can be abused when an adversary can enter privileged states~\cite{ali2014boundaryscanattack}.
Recent efforts add explicit authentication to JTAG/debug access, including lightweight
JTAG authentication IP and Schnorr-based identity schemes~\cite{lapeyre2022jtagauth,wang2020schnorrjtag}.
Practical JTAG debug infrastructures and emulation tools further motivate treating
debug enablement as a privileged capability~\cite{vandelogt2003jtag,walimbe2014jtagaxi,chen2008jtagemu}.

Hardware-enforced trusted execution and minimal-TCB designs provide isolation below
untrusted software. TrustZone-style partitioning, Keystone, TrustLite, and secure
processor designs illustrate different points in the isolation and deployment space,
while minimal-TCB and software root-of-trust work emphasizes small, auditable bases of
trust~\cite{zhang2017trustzoneeval,lee2020keystone,koeberl2014trustlite,suh2005aegis,mccune2007minimaltcb,gligor2019establishing,costan2017secureprocessors,ahmed2025riscvtee}.

Finally, deployable low-level mechanisms require toolchain support. LLVM-based
infrastructures enable analysis and instrumentation, and ISA extensibility (e.g.,
RISC-V) supports custom instruction integration that remains compatible with standard
toolchains~\cite{lattner2004llvm,shen2012llbt,zakai2011emscripten,waterman2014riscv}.
This motivates instruction-triggered authorization that is emitted and preserved by
the compiler and binary utilities.
