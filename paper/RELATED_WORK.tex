\section{Related Work}
\label{sec:relatedwork}

Embedded platforms are deployed in environments where adversaries can obtain physical
access and target programming/debug interfaces. Prior work spans BootROM-centered
secure boot, longer boot chains (e.g., OS/FPGA-style stacks), debug/test interface
security, hardware-enforced trusted execution and minimal TCB designs, software-only
hardening, and compiler/toolchain infrastructure for deployable low-level mechanisms.
This section reviews these lines and motivates instruction-triggered, key-gated
authorization with toolchain support.

\subsection{BootROM-Based Secure Boot and Early-Stage Integrity}
Secure boot anchors trust in immutable first-stage code (BootROM/ROM-resident loader)
that authenticates subsequent software. Bin \emph{et al.} design BootROM support for
secure boot mode and focus on validating system images during
startup~\cite{bin2020bootrom}. Rashmi R.\,V. and Karthikeyan survey secure boot
techniques for embedded applications and highlight practical
constraints~\cite{rv2018securebootreview}. These works establish boot-time authenticity
but leave \emph{post-boot} debug/program authorization open under physical-access
threats.

A related line of work extends boot trust into device identity and measurement chains.
J{\"a}ger and Petri present a hardware implementation of the Device Identifier
Composition Engine (DICE) for bootstrapping device
trust~\cite{jaeger2020diceharder}. Surveys discuss trade-offs across embedded platforms,
and measured-boot techniques establish trust properties over commodity systems and
their boot stacks~\cite{wang2022securebootsurvey,parno2010bootstrapping}.

\subsection{Boot-Chain Protection for Richer Stacks (Embedded Linux / FPGA Systems)}
As embedded systems incorporate more complex boot sequences (multiple software stages,
configuration artifacts, and OS components), integrity must extend beyond a single
image check. Devic \emph{et al.} address this problem for an embedded Linux boot flow on
FPGA by verifying artifacts in a multi-stage
chain~\cite{devic2011fpga}.

\subsection{Debug/Test/Programming Interface Security}
Debug and test access are high-impact attack surfaces because they provide invasive
control over execution, memory, and device state. IEEE~1149.1 standardizes the test
access port and boundary-scan architecture~\cite{ieee1149_1}, and boundary-scan/test
modes can be abused when an adversary enters privileged
states~\cite{ali2014boundaryscanattack}. Recent work adds explicit authentication to
debug access; for example, Lapeyre \emph{et al.} propose a lightweight JTAG
authentication IP to restrict unauthorized
usage~\cite{lapeyre2022jtagauth}.

Additional work examines authenticated or enhanced debug access mechanisms. Schnorr-
based identity authentication has been explored for secure JTAG debugging
models~\cite{wang2020schnorrjtag}, while other efforts extend JTAG for at-speed debug or
provide JTAG-based debug IP implementations and emulation
tools~\cite{vandelogt2003jtag,walimbe2014jtagaxi,chen2008jtagemu}. Together, these works
motivate treating debug enablement as a privileged capability and binding it to
explicit authorization.

\subsection{Hardware-Enforced Trusted Execution and Minimal-TCB Approaches}
TrustZone-style partitioning provides a widely deployed model for separating a trusted
execution domain from the normal execution environment; evaluations highlight attack
surfaces in heterogeneous SoCs~\cite{zhang2017trustzoneeval}. Open-platform efforts such
as Keystone demonstrate TEEs with explicit, auditable
interfaces~\cite{lee2020keystone}. TrustVisor, Flicker, and Memoir motivate minimizing
trusted code while maintaining measured execution and continuity
guarantees~\cite{mccune2010trustvisor,mccune2008flicker,parno2011memoir}, and TrustLite
targets constrained devices~\cite{koeberl2014trustlite}.

Secure-processor and minimal-context execution designs provide additional perspective
below untrusted software. AEGIS proposes a single-chip secure processor
model~\cite{suh2005aegis}, and minimal TCB code-execution frameworks reduce trusted
code footprint for sensitive operations~\cite{mccune2007minimaltcb}. Surveys add context
on enclave-style designs and assumptions~\cite{costan2017secureprocessors,ahmed2025riscvtee},
and software-root-of-trust designs address trust establishment without large trusted
stacks~\cite{gligor2019establishing}.

\subsection{Runtime Integrity and Attestation for Embedded Systems}
Beyond boot-time authenticity, several approaches provide evidence of runtime integrity
and control-flow correctness. Remote attestation mechanisms for embedded systems have
been studied in various forms~\cite{kylanpaa2016remoteattest}, and cumulative
attestation kernels extend attestation by accumulating evidence across
execution~\cite{lemay2012cumulative}. Collective attestation coordinates attestation
across devices in embedded networks~\cite{ibrahim2018collectiveatt}.

Control-flow attestation is a lightweight alternative to full-blown runtime monitoring.
C-FLAT attests control-flow by instrumenting software and producing
reports~\cite{abera2016cflat}, while LO-FAT demonstrates a low-overhead, hardware-
assisted direction~\cite{dessouky2017lofat}. Additional log-based and
micro-architectural attestation methods have been
proposed~\cite{liu2019logbasedcfa,benyehuda2022nanovised}. These lines are complementary
to key-gated authorization: rather than preventing unauthorized programming/debug
directly, they provide evidence about executed control flow and runtime state.

\subsection{System Assurance via Formal Verification}
Because low-level enforcement mechanisms are security-critical, prior work emphasizes
formal verification as a path to high assurance. The seL4 microkernel demonstrates
formal verification at the operating-system kernel
level~\cite{klein2009sel4,klein2014tocs}.

\subsection{Software-Only Hardening: Obfuscation and Key-Dependent Checks}
Software protection techniques deter tampering and reverse engineering by transforming
code or embedding secret-dependent checks; taxonomies summarize layered obfuscation
techniques and security goals~\cite{tran2020layered}.

Related work in software-only enforcement also includes control-flow protection and
exploitation models. Control-Flow Integrity (CFI) constrains indirect control transfers
to a precomputed graph~\cite{abadi2005cfi}, while return-oriented programming (ROP)
demonstrates attacks built from existing code snippets and motivates defenses that
restrict sensitive execution paths~\cite{checkoway2010rop}. These are not direct
substitutes for device-bound authorization but contextualize the broader threat
landscape.

\subsection{Toolchain Infrastructure, ISA Extensibility, and Deployable Low-Level Mechanisms}
Many enforcement mechanisms require reliable support from the compiler and binary
utilities. Shen \emph{et al.} present LLBT, an LLVM-based static binary
translator~\cite{shen2012llbt}; Zakai introduces Emscripten, an LLVM-to-JavaScript
compiler~\cite{zakai2011emscripten}; and RISC-V’s extensibility supports custom
instruction integration with conventional toolchains~\cite{waterman2014riscv}. LLVM is
widely used for program analysis and transformation, enabling compiler-integrated
instrumentation relevant to ISA-level
primitives~\cite{lattner2004llvm}. This motivates implementing authorization
instructions through toolchain support rather than binary rewriting.
