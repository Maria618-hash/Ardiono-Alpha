\section{Related Work}
\label{sec:relatedwork}

Embedded platforms are deployed in environments where adversaries can obtain physical
access and target programming/debug interfaces. Prior work spans BootROM-centered
secure boot, longer boot chains (e.g., OS/FPGA-style stacks), debug/test interface
security, hardware-enforced trusted execution and minimal TCB designs, software-only
hardening, and compiler/toolchain infrastructure for deployable low-level mechanisms.
This section reviews these lines and motivates instruction-triggered, key-gated
authorization with toolchain support.

\subsection{Boot Integrity and Device Identity}
Secure boot anchors trust in immutable first-stage code (BootROM/ROM-resident loader)
that authenticates subsequent software. Measured boot establishes trust properties
over commodity boot stacks~\cite{parno2010bootstrapping}, and multi-stage boot-chain
protection addresses richer embedded Linux/FPGA flows~\cite{devic2011fpga}. Surveys then
summarize secure-boot techniques and practical constraints in embedded
deployments~\cite{rv2018securebootreview}, and BootROM designs focus on validating
system images during startup~\cite{bin2020bootrom}. A related line of work extends boot
trust into device identity and measurement chains: DICE provides a hardware mechanism
for device identity composition~\cite{jaeger2020diceharder}, and more recent surveys
discuss trade-offs across embedded platforms and deployment
models~\cite{wang2022securebootsurvey}. These works establish boot-time authenticity
but leave \emph{post-boot} debug/program authorization open under physical-access
threats.

\subsection{Debug Access, Trusted Execution, and Runtime Protection}
Debug and test access are high-impact attack surfaces because they provide invasive
control over execution, memory, and device state. Early work extends JTAG for at-speed
debug and emulator implementations~\cite{vandelogt2003jtag,chen2008jtagemu}; IEEE~1149.1
later standardizes the test access port and boundary-scan
architecture~\cite{ieee1149_1}. Boundary-scan/test modes can be abused when an adversary
enters privileged states~\cite{ali2014boundaryscanattack}. More recent work adds
explicit authentication to debug access, including JTAG authentication IP and Schnorr-
based identity schemes~\cite{walimbe2014jtagaxi,wang2020schnorrjtag,lapeyre2022jtagauth}.

Hardware-enforced trusted execution evolved from secure-processor and minimal-TCB
designs (AEGIS and minimal TCB code execution)~\cite{suh2005aegis,mccune2007minimaltcb},
to measured-execution systems such as Flicker, TrustVisor, and Memoir, and to
constrained-device designs such as TrustLite~\cite{mccune2008flicker,mccune2010trustvisor,parno2011memoir,koeberl2014trustlite}.
TrustZone evaluations highlight attack surfaces in heterogeneous
SoCs~\cite{zhang2017trustzoneeval}, and Keystone demonstrates TEEs with explicit,
auditable interfaces~\cite{lee2020keystone}. Surveys add context on enclave-style
designs and assumptions~\cite{costan2017secureprocessors,ahmed2025riscvtee}, while
software-root-of-trust work addresses trust establishment without large trusted
stacks~\cite{gligor2019establishing}.

Runtime integrity mechanisms provide complementary evidence. Cumulative attestation
kernels (2012) extend attestation by accumulating evidence across
execution~\cite{lemay2012cumulative}, followed by remote attestation for embedded
systems~\cite{kylanpaa2016remoteattest} and collective attestation across embedded
networks~\cite{ibrahim2018collectiveatt}. Control-flow attestation progresses from
C-FLAT (2016) to LO-FAT (2017) and later log-based and micro-architectural
approaches~\cite{abera2016cflat,dessouky2017lofat,liu2019logbasedcfa,benyehuda2022nanovised}.
Formal verification (seL4, 2009/2014) provides high-assurance evidence for critical
code~\cite{klein2009sel4,klein2014tocs}. Software-only hardening includes CFI (2005),
ROP-based attack models (2010), and obfuscation taxonomies
(2020)~\cite{abadi2005cfi,checkoway2010rop,tran2020layered}. These techniques are
complementary to device-bound authorization and contextualize the broader threat
landscape.

\subsection{Toolchain and ISA Extensibility}
Many enforcement mechanisms require reliable support from the compiler and binary
utilities. LLVM provides a foundation for program analysis and
transformation~\cite{lattner2004llvm}. Emscripten and LLBT show LLVM-based retargeting
and binary translation~\cite{zakai2011emscripten,shen2012llbt}. RISC-V’s extensibility
supports custom instruction integration with conventional
toolchains~\cite{waterman2014riscv}. This motivates implementing authorization
instructions through toolchain support rather than binary rewriting.
In practice, compiler-integrated mechanisms also improve reproducibility and audit
because the authorization primitive is visible in emitted binaries and can be verified
in standard build logs and disassembly workflows.
